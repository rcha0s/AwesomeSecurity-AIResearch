## TL;DR

_The gist, not every detail - read the [full source](https://unit42.paloaltonetworks.com/monitoring-npm-supply-chain-attacks/) for the complete write-up._

Unit 42's rolling ledger of the post-Shai-Hulud npm compromise era. Since the September 2025 self-replicating worm, adversary TTPs have shifted along three axes: wormable propagation via stolen npm/GitHub PATs, infrastructure-level persistence via CI/CD embed, and multi-stage dormant payloads that evade scanners. The dossier documents Bitwarden CLI (April 2026), SAP @cap-js (April 29), TanStack (May 11 - first case of a worm publishing packages with valid SLSA Build Level 3 provenance via OIDC token extraction from /proc/<Runner.Worker>/mem), @antv (May 19, 639 malicious versions in one hour), @redhat-cloud-services (June 1, 32 packages with valid SLSA provenance), and AsyncAPI (July 14, unprotected pre-production release branches exploited). Notably: on July 14, GitHub Copilot's automated dependency loading imported a trojanized @asyncapi/specs@6.11.2 on a developer machine - 'the developer did not run npm install manually. The tooling did it for them.'

## What to learn

- SLSA Build Level 3 provenance is now confirmed-bypassable: a worm can publish signed packages with valid attestations because provenance only certifies which pipeline built the artifact, not that the pipeline's state was clean when it built. - _"This is the first documented case of a worm publishing malicious npm packages with valid SLSA Build Level 3 provenance. Sigstore correctly attested that the packages were built by release.yml from refs/heads/main of TanStack/router - because they were. SLSA provenance confirms which pipeline built a package, not whether that pipeline's internal state was clean."_ ✅
- The GitHub Actions cache is a poisonable pivot: actions/cache@v5 saves with a runner-internal token that is not gated by workflow permissions, and a fork's pull_request_target run can pre-compute the exact key a later release workflow will hit. - _"The fork's code wrote a 1.1 GB poisoned pnpm store under the exact cache key that release.yml would later look up. The key was pre-computed from the public pnpm-lock.yaml using the same hashFiles() formula the workflow uses. The poisoned cache entry then sat dormant for eight hours. A critical detail: actions/cache@v5's post-job save uses a runner-internal token, not the workflow GITHUB_TOKEN, so setting permissions: contents: read on the workflow does not prevent the cache write."_ ✅
- AI coding assistants are already the delivery mechanism: on a compromised macOS machine, Copilot's automatic dependency load pulled the trojanized package - the human never typed npm install. - _"On July 14, 2026, Unit 42 researchers analyzed a compromised macOS developer machine on which the developer opened a project workspace in GitHub Copilot. When the copilot parsed the workspace and triggered automated dependency loading, it imported the trojanized @asyncapi/specs@6.11.2 package. This silently launched the Stage-1 loader, which fetched Miasma sync.js from IPFS and spawned it under Homebrew Node.js v22, initiating active beaconing to 85.137.53[.]71:8080. The developer did not run npm install manually. The tooling did it for them."_ ✅
- --ignore-scripts is a partial control: preinstall hooks are only one delivery path, and a bin field can re-arm the payload the next time the user or any script invokes the compromised binary name (bw in the Bitwarden case). - _"Since the legitimate Bitwarden CLI also uses bw as its binary name, this serves as a secondary trigger. Even if preinstall is blocked (e.g., via --ignore-scripts), the malware executes the next time the user or any script invokes bw."_ ✅

## Threat · Conditions · Mitigations

- **Threat:** Enterprise developer environments - human workstations and CI/CD runners alike - where any AI coding assistant with dependency-resolution authority (Copilot workspace scan, Cursor MCP, Claude Code) can import a package before any pre-install control (CVE check, registry allowlist, human review) fires.
- **Conditions:** AI coding assistant is authorized to load or install project dependencies without explicit per-package approval. Registry policy is enforced only at CI, not at developer workstations, or vice versa. SLSA provenance is treated as sufficient rather than necessary-but-not-sufficient. GitHub Actions cache write is not gated per-workflow (default configuration). OIDC trusted-publisher bindings are scoped to the repo rather than a specific protected workflow.
- **Mitigations:** Enforce registry mediation (Socket Firewall / npm staged publishing / JFrog Curation) at both CI and developer workstation. Combine SLSA provenance verification with behavioral analysis at install time. Restrict AI coding agents to a pre-approved dependency allowlist in sensitive projects. Bind OIDC trusted publishers to a specific workflow on a specific protected branch, not a repo. Extend branch protection and code review requirements to every branch that triggers a release workflow, including pre-production and schema branches. Rotate npm and GitHub PATs after any incident and confirm every token was revoked before publishing new versions.
